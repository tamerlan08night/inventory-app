# RPG Inventory System — як пояснити проєкт

Конспект для захисту шкільного проєкту. Тут — що говорити, де в коді це лежить і як відповідати на питання про React.

---

## 1. Як почати розповідь (30 секунд)

> «Це веб-застосунок — менеджер інвентарю для RPG. Є персонаж із здоров'ям, калоріями та водою, сітка предметів, хотбар, спорядження, рюкзак, який додає клітинки й вантажопідйомність, і симуляція часу: потреби поступово зменшуються, від голоду й спраги падає здоров'я, а якщо потреби задоволені — здоров'я повільно відновлюється. Прогрес зберігається в `localStorage`, тобто після перезавантаження нічого не зникає.»

Далі — «стек»: **React 19 + Vite + звичайний CSS**. Без бібліотек UI і без бекенду.

## 2. Архітектура: хто за що відповідає

```
main.jsx
└── App.jsx                     ← стан застосунку + композиція
    ├── NavBar.jsx              ← перемикання вкладок
    └── ContentView.jsx         ← що показати для активної вкладки
        ├── InventoryWorkspace.jsx
        │   ├── PlayerPanel.jsx     ← здоров'я, одяг, body.png
        │   │   └── SurvivalModal.jsx
        │   ├── InventoryGrid.jsx   ← сітка 8×N, drag & drop, DEV
        │   │   └── dev/DevSpawnModal.jsx
        │   └── Hotbar.jsx
        └── TabView.jsx         ← Research / Manual / Statistics / ...

hooks/
├── useInventory.js   ← логіка інвентаря, стаків, спорядження, рюкзака
└── useSurvival.js    ← здоров'я, вода, калорії, таймер

data/    ← константи й довідники (не React)
utils/   ← чисті функції (наприклад, текст тултипа)
```

**Головна ідея архітектури:** *компоненти показують, хуки рахують.* Компоненти не знають, як працює стакування чи таймер — вони отримують дані й функції через `props` і малюють інтерфейс.

| Файл | Відповідальність |
|---|---|
| `App.jsx` | Тільки стан і збирання сторінки. 24 рядки. |
| `useInventory.js` | Предмети, стакінг, переміщення, спорядження, рюкзак, вага |
| `useSurvival.js` | Потреби, таймер, регенерація/шкода, збереження |
| `InventoryGrid.jsx` | Візуальна сітка, drag & drop, кнопки, DEV |
| `DevSpawnModal.jsx` | Форма створення предметів (контрольовані інпути) |

Це називається **розділення відповідальності**: `App` не містить логіки, а хуки не містять розмітки.

## 3. Потік даних (одне речення, яке варто вивчити)

> «Стан живе у `App` і в кастомних хуках. Вниз він передається через `props`, а змінюється — через функції-колбеки, які теж передаються вниз. Дитина ніколи не змінює батьківський стан напряму.»

Приклад:

```jsx
// App.jsx
const survival = useSurvival();
const inventoryState = useInventory({ onConsume: survival.consume });
...
<ContentView inventoryState={inventoryState} survival={survival} />
```

`useInventory` отримує функцію `survival.consume` і викликає її, коли гравець з'їв предмет. Так інвентар і потреби залишаються незалежними, але можуть взаємодіяти.

## 4. Які React-можливості використані (таблиця-шпаргалка)

| Що | Де саме | Навіщо |
|---|---|---|
| `useState` | `App`, `InventoryGrid`, `PlayerPanel`, `DevSpawnModal`, `ResearchTab`, `useInventory`, `useSurvival` | «Пам'ять» компонента: значення, яке при зміні перемальовує UI |
| `useEffect` | `useInventory` (×3), `useSurvival` (×2), `DevSpawnModal`, `SurvivalModal` | Побічні дії: збереження, таймер, підписка на клавіатуру |
| `useRef` | `DevSpawnModal` | Посилання на DOM-елемент (автофокус на інпуті) |
| Кастомні хуки | `useInventory`, `useSurvival` | Винести логіку зі стану з компонентів |
| `props` + колбеки | усі компоненти | Передача даних вниз / подій вгору |
| `createPortal` | `DevSpawnModal`, `SurvivalModal` | Модалка рендериться в `document.body`, а не всередині панелі |
| Умовний рендер | `ContentView`, модалки, поля DEV | `{isOpen && <Modal />}` |
| Списки + `key` | `NavBar`, `InventoryGrid`, `Hotbar`, `SPEED_OPTIONS.map` | React розуміє, який елемент який |
| Контрольовані інпути | `DevSpawnModal` | Значення інпута = стан React |
| `createRoot` | `main.jsx` | Точка входу React-застосунку |
| `StrictMode` | `main.jsx` | Режим розробки: підказки про помилки, подвійний виклик ефектів |

**Чого тут немає і чому:** `useMemo`, `useCallback`, `useReducer`, `useContext`, Redux, React Router, TypeScript. Проєкт малий — ці інструменти додали б складності без користі. Це сильна відповідь на питання «чому ви це не використали».

## 5. Розбір ключових місць (що говорити біля коду)

### 5.1 `useState`

```jsx
const [activeTab, setActiveTab] = useState('inventory');
```

> «`useState` повертає пару: поточне значення і функцію, яка його змінює. Коли я викликаю `setActiveTab`, React перемальовує компонент, і вкладка змінюється.»

Приклад зі станом-об'єктом (форма DEV):

```jsx
const [form, setForm] = useState(DEFAULT_FORM);
const setField = (field, value) =>
    setForm((previous) => ({ ...previous, [field]: value }));
```

> «Тут один об'єкт на всю форму. `setField` створює новий об'єкт, а не змінює старий — це важливо, бо React порівнює посилання.»

**Лінива ініціалізація:**

```jsx
const [survival, setSurvival] = useState(loadSurvivalState);
```

> «Якщо передати функцію, React викличе її лише один раз при створенні компонента. Це потрібно, щоб читати `localStorage` не при кожному рендері.»

### 5.2 `useEffect` — три різні випадки

**1) Збереження в localStorage** (`useInventory`, `useSurvival`):

```jsx
useEffect(() => {
    localStorage.setItem(STORAGE_KEY, JSON.stringify(survival));
}, [survival]);
```

> «Кожного разу, коли змінюється `survival`, ефект записує його в `localStorage`. Масив `[survival]` — це залежності: ефект запускається тільки коли вони змінюються.»

**2) Таймер** (`useSurvival`):

```jsx
useEffect(() => {
    if (!survival.isFlowing) return undefined;

    const intervalId = setInterval(() => {
        setSurvival((previous) => { /* ... */ });
    }, 1000);

    return () => clearInterval(intervalId);
}, [survival.isFlowing, survival.speed]);
```

> «Ефект створює інтервал. `return` — це cleanup: він прибирає старий інтервал, коли ефект перезапускається або компонент зникає. Без цього інтервали б множилися й час ішов би швидше.»

**3) Підписка на клавіатуру** (`SurvivalModal`, `DevSpawnModal`):

```jsx
useEffect(() => {
    const handleKeyDown = (event) => {
        if (event.key === 'Escape') onClose();
    };

    document.addEventListener('keydown', handleKeyDown);
    document.body.style.overflow = 'hidden';

    return () => {
        document.removeEventListener('keydown', handleKeyDown);
        document.body.style.overflow = previousOverflow;
    };
}, [onClose]);
```

> «Це синхронізація з зовнішнім світом — DOM. На `Escape` модалка закривається, поки вона відкрита — сторінка не скролиться. Cleanup повертає все як було.»

### 5.3 `useRef`

```jsx
const nameInputRef = useRef(null);
...
<input ref={nameInputRef} ... />
...
nameInputRef.current?.focus();
```

> «`useRef` зберігає посилання між рендерами й не викликає перемальовування. Тут — щоб поставити курсор в інпут при відкритті модалки.»

### 5.4 Кастомний хук

```jsx
export default function useInventory({ onConsume } = {}) {
    const [inventory, setInventory] = useState(...);
    // ...
    return { inventory, hotbar, equipment, addItem, removeItem, /* ... */ };
}
```

> «Кастомний хук — це звичайна функція, назва якої починається з `use`. Вона може викликати інші хуки. Завдяки цьому логіка інвентаря живе окремо, а `InventoryGrid` займається тільки картинкою.»

**Важливо:** хуки не можна викликати в умовах (`if`), циклах чи після `return`, бо React зберігає їхній стан за порядком виклику. Тому в `useInventory` всі `useState`/`useEffect` — на початку функції, без умов.

### 5.5 `props` і «підняття стану»

> «Стан інвентаря потрібен і сітці, і хотбару, і панелі персонажа. Тому він лежить вище — у `useInventory`, а не в кожному компоненті. Це називається lifting state up: спільний стан піднімається до спільного батька.»

Приклад: `InventoryGrid` не має власного списку предметів — він отримує `inventory` через `props`.

### 5.6 Списки та `key`

```jsx
{inventory.map((item, index) => (
    <div key={index} className="inventory-slot ...">
))}
```

> «`map` перетворює масив даних на масив JSX. `key` допомагає React зрозуміти, який елемент той самий після зміни. Для сітки з фіксованими слотами індекс — прийнятний ключ; для списків, які сортуються, краще `id`.»

### 5.7 `createPortal`

> «Модалка рендериться не всередині панелі, а прямо в `document.body`. Інакше `backdrop-filter` на батьківській панелі ламає `position: fixed`, і модалка опиняється не по центру екрана. Це реальний баг, який я так виправив.»

```jsx
return createPortal(<div className="dev-modal-overlay">...</div>, document.body);
```

### 5.8 Похідні значення (derived state)

```jsx
const currentWeight = [...inventory, ...hotbar, ...Object.values(equipment)]
    .reduce((acc, item) => acc + (item ? item.weight * (item.count || 1) : 0), 0)
    .toFixed(1);
```

> «Вага не зберігається в стані. Вона рахується зі стану при кожному рендері. Це принцип: якщо значення можна обчислити — не треба тримати його в `useState`, інакше воно може розсинхронізуватися.»

Так само `weightPercent`, `totalSlots`, `maxWeight`.

## 6. «Які функції React можна переписати?» — головна відповідь

Питання вчителя, швидше за все, означає: *«що тут можна було б зробити інакше / краще»*. Ось чесні варіанти з плюсами й мінусами.

### 6.1 Три `useState` в `useInventory` → один `useReducer`

**Зараз:**

```jsx
const [inventory, setInventory] = useState(...);
const [hotbar, setHotbar] = useState(...);
const [equipment, setEquipment] = useState(...);
```

**Можна:** об'єднати в один стан або `useReducer` зі «сценаріями»:

```jsx
// ескіз
const [state, dispatch] = useReducer(inventoryReducer, initialState);
dispatch({ type: 'addItem', item });
dispatch({ type: 'equip', index, slot: 'backpack' });
```

**Плюси `useReducer`:** одна функція описує всі зміни, зручно тестувати, менше ймовірність забути оновити частину стану.
**Мінуси:** більше коду; для трьох незалежних списків `useState` читається простіше.
**Що сказати:** «Технічно можна, але зараз стан розділений логічно: інвентар, хотбар, спорядження. Якби додав, наприклад, скрині чи торгівлю — перейшов би на `useReducer`.»

### 6.2 Форма DEV → `useReducer` або окремий хук `useSpawnForm`

Зараз 11 полів в одному об'єкті й універсальний `setField`. Це вже компактно, але валідацію можна винести.

**Що сказати:** «Я обрав один об'єкт форми, щоб не мати 11 `useState`. Валідацію рахую з нього ж — окремих `useState` для помилок немає.»

### 6.3 Три `useEffect` для збереження → кастомний хук `useLocalStorage`

**Зараз:** три майже однакові ефекти.

**Можна:**

```jsx
// ескіз
function useLocalStorage(key, initialValue) {
    const [value, setValue] = useState(() => {
        const saved = localStorage.getItem(key);
        return saved ? JSON.parse(saved) : initialValue;
    });

    useEffect(() => {
        localStorage.setItem(key, JSON.stringify(value));
    }, [key, value]);

    return [value, setValue];
}
```

**Плюс:** прибрав би дублювання.
**Мінус:** для трьох різних сховищ це економить 6 рядків, але додає ще один файл.
**Що сказати:** «Це гарний рефакторинг на майбутнє. Зараз я залишив явні ефекти, щоб було видно, що саме зберігається.»

### 6.4 Похідні обчислення → `useMemo`

**Зараз:** `currentWeight` рахується при кожному рендері.

**Можна:**

```jsx
const currentWeight = useMemo(() => {
    /* reduce */
}, [inventory, hotbar, equipment]);
```

**Чому зараз не треба:** максимум 64 предмети — це мікросекунди. `useMemo` має сенс при дорогих обчисленнях (сотні тисяч елементів, складні фільтри).
**Що сказати:** «Я знаю про `useMemo`, але це передчасна оптимізація. Виміряв би проблему — тоді додав.»

### 6.5 Колбеки → `useCallback` / `React.memo`

Те саме: поки що немає дорогих дочірніх компонентів, які варто мемоізувати.
**Що сказати:** «`useCallback` потрібен, коли дочірній компонент обгорнутий у `memo` і ми хочемо зберегти посилання на функцію. У мене таких немає.»

### 6.6 Prop drilling → `useContext`

`InventoryWorkspace` приймає ~15 пропсів і передає далі. З `Context` можна було б зробити так:

```jsx
<InventoryProvider>
    <InventoryWorkspace />
</InventoryProvider>

// у будь-якому компоненті
const { inventory, addItem } = useInventoryContext();
```

**Плюс:** менше «прокидування» пропсів через проміжні компоненти.
**Мінус:** складніше зрозуміти, звідки приходять дані; для 3 рівнів вкладеності це не потрібно.
**Що сказати:** «Context виправданий на 5+ рівнях або коли дані потрібні багатьом гілкам. У мене дерево дрібне, тому явні пропси зрозуміліші.»

### 6.7 `setInterval` → таймер на реальному часі

**Зараз:** інтервал раз на секунду, кожен тік додає/віднімає фіксовану кількість.

**Проблема:** якщо вкладка «засинає», браузер сповільнює таймери; інтервал також може «дрейфувати».
**Можна:** рахувати час через `performance.now()` або `requestAnimationFrame` з дельтою.

**Що сказати:** «Для навчального симулятора секундного кроку достатньо. У грі з важливою економікою часу я б рахував дельту між кадрами.»

### 6.8 `alert()` → власна модалка/toast

`alert` блокує сторінку й виглядає нерідно до стилю. Можна зробити `useToast` або модалку в стилі застосунку.
**Що сказати:** «Це технічний борг, який я знаю: `alert` — швидкий спосіб для перевірки, у фінальній версії замінив би на компонент.»

### 6.9 `localStorage` → IndexedDB або бекенд

**Що сказати:** «`localStorage` — найпростіший варіант без сервера: до 5 МБ, синхронний, зберігає лише рядки. Для акаунтів і синхронізації між пристроями потрібен бекенд і база даних.»

### 6.10 Дрібниці, які вчитель може помітити

- `key={index}` у сітці — ок для фіксованих слотів, але при сортуванні краще `item.id`.
- `loadState` не має `try/catch`, а `loadSurvivalState` має — можна уніфікувати.
- `count` зберігається навіть у нестакувальних предметів (`count: 1`) — можна прибрати.
- Частина логіки рюкзака (розрахунок слотів) — у хуку, це добре; але обробку «куди подіти предмети при зменшенні» можна винести в окремий модуль.

## 7. Ймовірні питання вчителя + короткі відповіді

**Що таке React і навіщо він?**
> «Бібліотека для побудови інтерфейсу з компонентів. Головне, що вона робить: коли змінюється стан, сама оновлює DOM. Без неї я б вручну перемальовував сітку після кожної дії.»

**Що таке компонент?**
> «Функція, яка повертає JSX — опис розмітки. Компоненти можна вкладати й повторно використовувати, як `NavBar` або `Hotbar`.»

**Що таке хук?**
> «Функція React, яка дає компоненту можливості: `useState` — пам'ять, `useEffect` — побічні дії, `useRef` — посилання. Мої `useInventory`/`useSurvival` — кастомні хуки, що складають ці можливості разом.»

**Чому хуки не можна викликати в `if`?**
> «React зберігає стан хуків за порядком виклику. Якщо порядок зміниться між рендерами, React переплутає стани. Тому — тільки на верхньому рівні функції.»

**Чому `setState` не змінює значення одразу?**
> «React групує оновлення й перемальовує пізніше. Тому після `setX(1)` у тому ж рендері `x` ще старий. Якщо нове значення залежить від старого — використовую функцію-оновлювач: `setX(prev => prev + 1)`. У мене так зроблено в `useSurvival`, бо таймер щосекунди залежить від попередніх значень.»

**Навіщо масив залежностей в `useEffect`?**
> «Він каже React, коли перезапускати ефект. Порожній масив — один раз після монтування. Без масиву — після кожного рендеру (зазвичай помилка). У мене `[survival]` для збереження і `[survival.isFlowing, survival.speed]` для таймера.»

**Навіщо `return` в `useEffect`?**
> «Це cleanup: прибрати таймер, зняти слухач подій, повернути стилі. Він викликається перед наступним запуском ефекту й при розмонтуванні. Без нього — витік пам'яті й дублікати інтервалів.»

**Чому в dev-режимі ефект спрацьовує двічі?**
> «Це `StrictMode` у `main.jsx`: React навмисно запускає ефекти двічі, щоб знайти ті, які не мають cleanup. Мій таймер має cleanup, тому проблеми немає. У production-збірці такого немає.»

**Що таке кастомний хук?**
> «Функція з назвою `use...`, яка викликає інші хуки й повертає дані та функції. Це спосіб винести логіку з компонента. `useSurvival` — приклад: компонент не знає, як рахується шкода.»

**Навіщо `key` у `map`?**
> «Щоб React розпізнавав елементи між рендерами. Без ключа він оновлює список менш ефективно й може плутати стан елементів. Для фіксованих слотів я використовую індекс.»

**Що таке контрольований інпут?**
> «Коли `value` інпута береться зі стану, а `onChange` його оновлює. Тоді React — єдине джерело правди: можна валідувати, скидати, підставляти значення. Так зроблено у формі DEV.»

**Чому модалки через `createPortal`?**
> «Щоб модалка була нащадком `document.body`, а не панелі з `backdrop-filter`. Інакше CSS-контекст ламає `position: fixed`, і вікно з'їжджає.»

**Де зберігається стан і чому саме там?**
> «Спільний стан — у `App` і хуках. Локальний UI-стан (відкрита модалка, індекс перетягування) — у відповідному компоненті. Правило: стан живе там, де він потрібен, але не нижче.»

**Як працює drag & drop?**
> «Це HTML5 Drag and Drop API, не React. `draggable` на картці, `onDragStart` кладе індекс у `dataTransfer`, слот на `onDrop` читає його й викликає `onMoveItem`. React лише передає події.»

**Чи можна було зробити без React?**
> «Можна, але довелося б вручну синхронізувати DOM зі станом у десятках місць. React прибирає цю роботу.»

**Чому прогрес не зникає після перезавантаження?**
> «`useEffect` записує стан у `localStorage`, а `useState` з функцією-ініціалізатором читає його при старті. Формат — JSON.»

**Що буде, якщо `localStorage` пошкоджений?**
> «У `useSurvival` стоїть `try/catch` і перевірка типів — повертаються безпечні дефолти. У `useInventory` простіше: якщо JSON не парситься, буде помилка. Це місце можна покращити.»

**Чи використовували ви готові бібліотеки?**
> «Тільки React і Vite. UI, drag & drop, таймер, збереження — написані вручну. Це було частиною задачі.»

## 11. Додаток: `useEffect` поглиблено

### 11.1 Що це таке простими словами

Компонент — це функція, яка **малює** інтерфейс. Але іноді після малювання треба зробити щось «зовнішнє»: записати в `localStorage`, запустити таймер, повісити слухач клавіатури, змінити `body.style`. Ці дії називаються **побічними ефектами** (side effects).

> «`useEffect` — це інструкція React: після того, як ти намалював компонент, виконай ось цю дію. А коли компонент зникає або ефект перезапускається — прибери за собою.»

Аналогія: рендер — це фотографія. `useEffect` — це те, що ти робиш **після** фотографії (увімкнув світло, підписав, повісив на стіну). І `return` — це прибирання, коли фотографію знімають.

Важливо: ефект виконується **після** того, як React оновив DOM. Тому всередині вже можна звертатися до елементів.

### 11.2 Анатомія — кожна частина

```jsx
useEffect(() => {
    // 1. Тіло ефекту: що зробити
    const intervalId = setInterval(() => { /* ... */ }, 1000);

    // 2. Cleanup: що зробити перед наступним запуском / при зникненні
    return () => clearInterval(intervalId);
}, [survival.isFlowing, survival.speed]); // 3. Залежності: коли запускати
```

| Частина | Роль |
|---|---|
| Функція першим аргументом | Сама дія. Виконується після рендеру |
| `return () => {...}` | Прибирання. Необов'язкове |
| Другий аргумент — масив | «Коли перезапускати». Необов'язковий |

### 11.3 Три режими роботи (це питають найчастіше)

**Без другого аргументу** — після **кожного** рендеру:

```jsx
useEffect(() => {
    console.log('після кожного рендеру');
});
```

**Порожній масив `[]`** — один раз після першого рендеру (mount) і cleanup при зникненні:

```jsx
useEffect(() => {
    console.log('компонент з’явився');
    return () => console.log('компонент зник');
}, []);
```

**Масив із залежностями `[a, b]`** — при mount і щоразу, коли `a` або `b` **змінилися**:

```jsx
useEffect(() => {
    // запускається, коли змінилася швидкість або старт/пауза
}, [survival.isFlowing, survival.speed]);
```

React порівнює залежності з попереднім рендером через `Object.is` (для чисел і рядків — звичайне порівняння). Об'єкти, масиви й функції — це **нові посилання** при кожному рендері, тому ефект із ними в залежностях запускається щоразу. Це джерело половини помилок з `useEffect`.

### 11.4 Cleanup: як це працює в часі

```
mount:      render → effect
update:     render → cleanup(старий ефект) → effect(новий)
unmount:    cleanup
```

Приклад із таймером:

1. Натиснув **Start** → `isFlowing = true` → React рендерить → створюється інтервал.
2. Натиснув **Pause** → `isFlowing = false` → React рендерить → **cleanup** очищає інтервал → новий ефект бачить `false` і нічого не створює.
3. Перейшов на іншу вкладку сайту (компонент зник) → **cleanup** знову очищає інтервал.

Без cleanup інтервали б накопичувалися: два Start/Pause — два інтервали, і час ішов би вдвічі швидше.

### 11.5 П'ять ефектів у цьому проєкті

| Файл | Що робить | Залежності | Cleanup |
|---|---|---|---|
| `useInventory.js` ×3 | Зберігає інвентар / хотбар / спорядження в `localStorage` | `[inventory]`, `[hotbar]`, `[equipment]` | не потрібен |
| `useSurvival.js` | Зберігає потреби | `[survival]` | не потрібен |
| `useSurvival.js` | Таймер: щосекунди зменшує воду/калорії, рахує здоров'я | `[survival.isFlowing, survival.speed]` | `clearInterval` |
| `DevSpawnModal.jsx` | `Escape` закриває, блокує скрол, ставить фокус | `[onClose]` | знімає слухач, повертає скрол |
| `SurvivalModal.jsx` | Те саме для вікна Survival | `[onClose]` | те саме |

**Чому `[onClose]`, а не `[]`?** Формально `onClose` — нова функція при кожному рендері батька. Ефект перезапускається, але це дешево й безпечно. Якби це було дорого — обгорнули б `onClose` у `useCallback`.

### 11.6 Чому `[survival]` для таймера — погано

Якби написати `}, [survival]);`, то `survival` змінюється **кожну секунду** (тік таймера), отже:

```
тік → setSurvival → render → cleanup → новий інтервал → тік → ...
```

Інтервал перестворювався б щосекунди. Працювало б, але марно й крихко. Тому в залежностях тільки те, від чого справді залежить **створення** інтервалу: `isFlowing` і `speed`.

А як же таймер бачить свіжі значення? Через **функцію-оновлювач**:

```jsx
setSurvival((previous) => {
    const water = clamp(previous.water - WATER_DRAIN_PER_SECOND * previous.speed, 0, MAX_WATER);
    // ...
    return { ...previous, water, calories, health };
});
```

> «Інтервал створюється один раз і не перезапускається. Кожен тік React передає в колбек **актуальний** попередній стан. Тому таймер не "застрягає" на значеннях, які були при його створенні.»

Це і є відповідь на питання «що таке stale closure і як ви його уникнули».

### 11.7 П'ять типових помилок

1. **Нескінченний цикл**: `useEffect(() => setX(x + 1))` без залежностей — кожен рендер змінює стан, який викликає рендер.
2. **`async` прямо в ефекті**: `useEffect(async () => { ... })` — повертає `Promise`, а React чекає функцію cleanup. Треба оголосити `async function` всередині й викликати її.
3. **Забутий cleanup**: таймери, `addEventListener`, WebSocket — усе це треба прибирати.
4. **Застарілі значення**: читати `state` із замикання в довгому інтервалі замість `setState(prev => ...)`.
5. **Обчислення в ефекті замість рендера**: `useEffect(() => setWeight(total), [...])` — зайвий рендер і риск розсинхрону. Похідні значення рахують прямо в тілі компонента.

### 11.8 Коли `useEffect` **не** потрібен

- **Похідні дані**: `currentWeight`, `weightPercent`, `totalSlots`, `maxWeight` — рахуються під час рендера.
- **Реакція на клік**: обробник події (`onClick`, `onDrop`), а не ефект.
- **Ініціалізація стану**: `useState(() => ...)` з функцією.
- **Синхронізація між двома станами**: майже завжди ознака того, що одне з них зайве.

Правило: **ефект потрібен лише для синхронізації із зовнішнім світом** (DOM, сховище, таймери, мережа, підписки).

### 11.9 Відповідь на 30 секунд

> «`useEffect` — це хук для побічних дій після рендеру. Він приймає функцію й масив залежностей. Порожній масив — один раз при появі компонента; масив зі значеннями — коли вони змінюються. Якщо ефект щось створює — таймер, слухач, підписку — він повертає функцію cleanup, яка це прибирає. У мене це збереження в `localStorage`, таймер потреб і закриття модалок на `Escape`.»

| Хук | Коли використовують | Чи є у проєкті |
|---|---|---|
| `useState` | Локальна пам'ять компонента | Так, скрізь |
| `useEffect` | Побічні дії після рендеру | Так, 7 разів |
| `useRef` | Посилання на DOM або значення без ре-рендеру | Так, автофокус |
| `useContext` | Дані без «прокидування» пропсів | Ні (дерево мале) |
